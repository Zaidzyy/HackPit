## 2. THE DIAGNOSTIC — why is headless refused? (~20 min, NO build)

### What is already known, and must not be re-measured

* **ZAP's own client passes Akamai.** All 55 captured requests were fetched *by ZAP* — Firefox
  spoke to ZAP, ZAP spoke to the target. So the upstream TLS stack and HTTP client are fine.
  The TLS-fingerprint theory is dead; do not resurrect it.
* Firefox → ZAP → target: **passes**.
* headless Chromium → ZAP → target: **ZAP's own 20s read timeout, 0 bytes**.
* headless Chromium → ZAP → `example.com`: **fine**.

So the discriminator is in what ZAP FORWARDED — the request headers the client set. The prime
suspect is one token: `User-Agent: …HeadlessChrome/150…`.

### Probes

All through the already-running proxy. Each is a single GET of a public page — negligible
volume, and the same page a browser already loaded.

**P0 — REPRODUCE THE FAILURE, 3×.** One measurement is not a result. Confirm the headless hang
is stable and not a transient or a rate-limit. If it is intermittent, STOP: everything below
assumes a deterministic discriminator, and an intermittent one is a different investigation.

**P1 — headless Chromium with a normal (non-headless) Chrome UA.**
Isolates the `HeadlessChrome` token specifically.
*This sends one spoofed UA as a MEASUREMENT.* Zaid has authorised the diagnostic; it does not
authorise shipping it.

**P2 — HEADED Chromium under Xvfb, stock UA, nothing spoofed.**
This is option A tested directly, and it is the outcome to hope for: a genuinely real browser,
no imitation.
Install `xvfb` into the RUNNING container (`apt-get update && apt-get install -y xvfb`) —
**do not rebuild the image for a diagnostic.** Then `Xvfb :99 &` and `DISPLAY=:99 chromium
--proxy-server=… <url>`.
TRAP (recorded): Kali ships some binaries with FILE capabilities and `no-new-privileges` makes
the kernel refuse to exec them. If Xvfb will not start, `setcap -r` the binary.

**P3 — capture the failure shape, not just "it failed."** For the hanging case, record whether
the TCP connection is accepted and then starved, or reset, and at which point. `curl -v` through
the proxy, or ZAP's own history entry.

### The decision table — write the outcome into the assessment BEFORE building anything

| P1 (spoofed UA) | P2 (headed/Xvfb) | conclusion | action |
|---|---|---|---|
| passes | passes | one header; the honest fix works | **Build option A** (Xvfb + `SPIDER_BROWSER_ID = "chrome"`). No spoofing needed. |
| passes | **fails** | only *imitation* works | **STOP. Ask Zaid.** This is a reversal of "nothing here imitates or evades — it uses one." It is his call, stated explicitly, not a tweak. |

## 4. RUNBOOK §3.4 — the scanner against the real target

**This is the highest-value untested thing in the build.** Part 3 replays *captured* requests,
which carry Firefox's headers — so the chain may hold end to end even though the spider does
not. Nobody has checked.

Prerequisite: item 1 must be done first.

**Pick the endpoint deliberately.** ZAP's active scanner sent **376 requests against a single
endpoint** in the build #14 measurement. Against a production retail site that is real load,
and the payloads go at every parameter.

* **Choose a READ-ONLY endpoint** — a search or catalogue URL with a query parameter.
* **Never** a cart, checkout, account, or newsletter path. Injection payloads at a checkout
  parameter on a live storefront can create orders or wipe a basket. This is the AJAX spider's
  hazard arriving through a different door.
* `recurse=false`. One URL.
* **THE SCAN IS NOT PACED.** Build #16's throttling is an `executor` feature and this path does
  not use it (see the note at the top). Watch `requests` climb on the `:proxy` scan panel and
  stop early if it is louder than expected — stop is ungated for exactly this reason, and here
  it is the only rate control there is.
* **If it reports zero findings, check #16's session-expiry flag before believing it.** Zero
  findings and a dead session look identical from the outside; that flag exists to tell them
  apart.

**Both outcomes matter:**
* **It works** → the captured-request → scanner chain survives a WAF. That is the pipeline you
  actually hunt with, confirmed.
* **It is refused** → the attack half is blocked even though capture works, which is a
  significantly larger finding than the spider's refusal and changes what build #15 delivers.

## 5. The two small fixes

**Chromium's background networking.** A crawl aimed at a local two-page site also produced
requests to `www.google.com`, `gstatic.com` and `play.google.com` — variations seed and search
preconnect, egressing through the proxy from a full-egress sandbox. Add to
`/etc/chromium.d/hackpit-container`:

```
--disable-background-networking --no-first-run --no-default-browser-check
```

Bundle with item 3's rebuild. **If item 3 does not happen, this is still worth its own rebuild**
— traffic nobody asked for, attributed to the operator's IP, is wrong for an engagement tool.

**Runbook §5 — teardown.** Remove `docker/listener-profile.yml` and recreate `engage-sandbox`.
Deleting the profile alone does NOT close the port; `exposure.observe()` reports that state as
`drifted`, never `none`.
