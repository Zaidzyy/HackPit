### The measurement that sequences this build

Verified 2026-08-05, and it is the reason nothing may be recreated casually:

| where | GraphQL add-on |
|---|---|
| the IMAGE, `/usr/share/zaproxy/plugin/` | **0.29.0** |
| the RUNNING container, `/root/.ZAP/plugin/` | **0.33.0** — a runtime auto-update |
| a fresh container from the image | **0.29.0 only** |

ZAP prefers `$HOME/.ZAP/plugin`. **So build #20's item-1 proof (56/0) measured 0.33.0 while the
image builds 0.29.0.** Recreate today and every one of those measurements is against an
implementation that is no longer present.

This is `api.disablekey` again — *a daemon that persists its configuration makes every
measurement conditional on what a previous run wrote* — one level worse, because what persisted
was an entire add-on version, i.e. a different implementation of the thing under test.

## 1. Pin the add-on, rebuild, recreate, and RE-MEASURE — in that order

The three leftovers collapse here. Do not reorder them.

* **Pin the GraphQL add-on version in the image** so the image and the measurement can never
  disagree again. 0.33.0 or newer, fetched at build time and placed where ZAP will load it, not
  left to a runtime auto-update. The version is now a build input, like `chromedriver` and
  `chromium` majors are.
* **Assert it at build time**, the way the chromedriver/chromium majors are asserted: the build
  fails if the add-on ZAP will actually load is not the pinned one. A layer that installs a file
  proves nothing about which file gets loaded — `$HOME/.ZAP/plugin` wins over the system dir, and
  that is exactly how this drift happened.
* **Then rebuild.** ~45 minutes. Bundle EVERY image change in this build into that one rebuild.
* **Then recreate the container.** This is what puts build #20's four GraphQL tools
  (`graphw00f`, `graphql-cop`, `inql`, `clairvoyance`) in reach of a run — leftover #2, free.
  It destroys the daemon and its capture; that is acceptable now and is the reason this is
  sequenced first rather than last.
* **Then RE-RUN `docs/proof/build20_graphql_api.py`** against the image-produced version.
  Upgrading changes the scanner engine, so **item 1's go/no-go must be answered again.** Treat
  the 56/0 as a regression baseline: reproduce it, and where 0.33.0-from-image differs from
  0.33.0-as-runtime-artefact, that difference is a finding — record it.
* Build #20 measured that ZAP **files none of its generated operations in the Sites tree**, which
  is why item 5 scans captured operations instead. **Re-check that specifically.** If the pinned
  version behaves differently, the scan path may improve; if it does not, say so and leave the
  captured-operation path alone.

## 2. Engine fingerprinting, in the product

Suggestion wording is per-implementation, so enumeration cannot start until the engine is known.

* Fingerprint the endpoint: Apollo, graphql-js, Hasura, Graphene at minimum, plus whatever else
  falls out cheaply (Ariadne, Strawberry, gqlgen, Absinthe, Juniper).
* Use response shape and error wording, not a banner — GraphQL servers do not announce themselves.
* `graphw00f` is now in the arsenal and does exactly this. **Decide deliberately** whether the
  product fingerprints natively or drives the tool, and write down which and why. Driving the tool
  keeps one implementation; doing it natively keeps it inside the gated, recorded path. Either is
  defensible — an unstated choice is not.
* **`unknown` is a real answer.** An engine you cannot identify must not be silently treated as
  Apollo; enumeration against the wrong parser produces confident nonsense.

## 3. Field-suggestion enumeration — the actual build

When introspection is off, many servers still answer a wrong field name with
`Did you mean "user"?`. That suggestion leaks the schema one field at a time.

* **A parser per engine.** The four named above each word suggestions differently; one regex over
  all of them is the shape this project has been burned by repeatedly. Each parser gets its own
  fixture and its own test.
* **Wordlist-driven**, with the wordlist and its size part of the approved surface — the same rule
  as crawl depth and scan policy: *a generator that decides its own bounds has stopped describing
  what runs.*
* **BOUND IT, and the bound is a declared parameter, NOT A GATE.** Enumeration is inherently
  high-volume — hundreds to thousands of requests. It takes a maximum request count and/or a
  wall-clock limit, set at start, visible, and read back. Stop stays ungated. This is not the
  scanner-wide request cap that was declined; it is one feature describing its own bounds.
* **THREE OUTCOMES, THREE ANSWERS, NEVER ONE `[]`.** Suggestions enabled and productive /
  suggestions **disabled** (`didYouMean` off — common in production) / request failed. Returning
  an empty schema for all three is the silent-empty class this codebase has now fixed four times.
  Build #20 already found `importUrl` returning the same code for introspection-disabled and a
  dead host — do not repeat that shape here.
* Reuse build #19's history/repeater plumbing rather than growing a second HTTP path.

## 4. What the recovered schema is FOR

A reconstructed schema is only worth the requests if something consumes it.

* Feed it to **build #20's repeater GraphQL mode** — recovered fields and arguments become
  something the operator can compose against, instead of guessing.
* Feed it to **the scan path** so a recovered argument can be attacked, which is the whole chain
  report #61 needed: no introspection → enumerate → aim at an argument.
* Persist it against the engagement so a report can say how the schema was obtained. A schema
  recovered by suggestion-mining is a different provenance from one handed over by introspection,
  and a report that blurs them is dishonest.

## 5. Two traps build #20 paid for — do not re-pay them

* **A PACKAGE UNDER THE EXPECTED NAME IS NOT THE PROJECT.** Build #20 found `graphw00f` and
  `graphql-cop` on PyPI to be inert placeholders — one whose own summary says it exists because a
  public agent skill names it. The real projects came from GitHub. Any tool added or driven in
  this build must be verified by **running it**, not by installing something with the right name.
* **`tsc`, `next build` and `eslint` cannot see whether a CSS class exists.** Build #20's Chrome
  pass found five defects they all passed through, including a shared CSS rule over-matching at
  21 sites across 7 components — fixed at the rule, not the screen, which is the right level.
  Read the `frontend-class-vocabulary` memory before touching a screen, and drive the real Chrome
  over everything this build touches.
