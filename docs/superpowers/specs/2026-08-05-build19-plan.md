**Date:** 2026-08-05
**Branch:** `main` (one branch, always)
**Predecessor:** build #18 ran at `bcb3bf5`; the curated exploit overlay and two source

## Why this build exists

Build #18 made HackPit *reach* the targets that were refusing it — curl-impersonate for the bare
tools, payload shaping past the WAF rules, authenticated scanning, a bypass-header mechanism.
What it did not touch is a gap measured afterwards, by comparing HackPit against Burp and Caido
rather than against its own backlog:

**HackPit's proxy records faithfully and cannot change anything mid-flight.**

That is the single biggest capability difference between it and Burp, and four things fall out of
it. Measured 2026-08-05 against the code, not assumed:

| gap | evidence | matters because |
|---|---|---|
| **intercept / modify in flight** | zero break/intercept references in `cockpit/proxy.py` | the core manual-testing loop; impossible today |
| **repeater cookie jar** | `repeater.py` keeps a per-session history ring, no cookie handling | every authenticated flow breaks on the second request |
| **history filtering** | `history(container, port, start, count)` — paging only | there are ~1,300 captured messages and no way to ask a question of them |
| **intruder-style fuzz of a captured request** | nothing; `ffuf`/`wfuzz` exist only as standalone argv | you cannot say "this parameter, these payloads, this captured request" |

**AND THE CORRECTION THAT MAKES THIS BUILD CHEAP.** The first advice given was "install Burp,
there is no prize for reimplementing it." That was wrong in one important way: **we are not
reimplementing interception, we are exposing ZAP's.** ZAP already implements a break/intercept
API inside the container HackPit already drives. This is a surfacing job, not a proxy-building
job — which is why item 4 is days rather than weeks.

## 1. VERIFY ZAP'S BREAK API FIRST — go/no-go for item 4

Nothing in item 4 may be built before this answers. Build #14 was written against
`zap-baseline.py`, which does not exist in Kali, and only the image build caught it. **An API
surface nobody measured is a plan with a hole in it.**

* Bring a daemon up (8090 is republished; `docker/proof/browser_intercept_proof.sh` drives its
  own, or start one from `:proxy`).
* Enumerate what ZAP 2.17.0 actually exposes under `break/` — the views and the actions, by name,
  with their parameters. `core/view/apiSummary` or the `/JSON/break/view/` index; do not trust
  the online docs for a version you are not running.
* **Write down what is there and what is not.** The shape this needs is: turn breaking on, learn
  a request is held, read it, replace it, forward it, drop it.
* If the API cannot do that, **say so and stop item 4** — record the negative result and build
  items 2, 3, 5 and 6. A recorded "ZAP cannot do this" is a legitimate outcome and is worth more
  than a half-feature.

## 2. Repeater cookie jar

The smallest item and it unblocks the most.

* A per-`session_id` cookie jar. `Set-Cookie` on a response is applied to subsequent sends
  against the same host, RFC 6265 rules (domain, path, expiry, `Secure`, `HttpOnly` is
  irrelevant here since we are not a browser).
* **The jar is state, and state that silently changes a request is a trap.** The response must
  say which cookies were attached and where they came from, so an operator reading a repeater
  exchange is never surprised by a header they did not type.
* An explicit way to clear the jar, and to send *without* it — testing what happens with no
  session is a real test.
* Cookies are credentials: they must not reach run records, the LLM prompt or a rendered report
  any more freely than they already do. Check what `report.py` redacts before assuming.

## 3. History filtering

There are ~1,300 captured messages and the only tool is `start`/`count`.

* Filter server-side over ZAP's history: host, method, status code, URL substring, has-parameter,
  content-type, and "in scope" (reuse `cockpit/scope.py` — do not re-derive scope anywhere).
* **Return the counts honestly**: matched, scanned, and — since build #18 — `dropped` and
  `read_ok`. A filter that silently searched only the newest window would be this repo's
  recurring silent-empty in a new place.
* This is a READ. It stays ungated, like the history it reads.

## 4. Interception — the real gap

Only if item 1 says the API is there.

* Turn breaking on/off; know when a request is held; read the held request; **replace it**;
  forward it; drop it.
* **This is human-in-the-loop by construction** — a request is held, a human edits it, a human
  forwards it. There is no gate to bypass because a human is the one pressing forward. Do not
  invent one.
* The frontend is most of the work. **Read the `frontend-class-vocabulary` memory BEFORE touching
  a screen**: bare `.hp-card` is `opacity:0`, screens use `hp-tn-*`, and tsc/build/eslint cannot
  see whether a CSS class exists. A frontend change is not verified until it has been LOOKED AT
  in a browser.
* A held request blocks the browser that made it. **Say so on screen** — an operator who forgets
  breaking is on will otherwise think the target went down. Consider a visible global indicator,
  and make "drop everything and turn breaking off" reachable in one click.

## 5. Intruder — a captured request, positions, one approval

* Take a captured request, mark payload positions in it, take a wordlist or a generated set,
  and run.
* **THIS FITS THE MODEL AND HERE IS WHY, so nobody re-litigates it.** HackPit refuses *batching
  across approvals*; it has never refused one approval that produces many requests — `ffuf`,
  `nuclei` and the ZAP active scanner are each a single approval buying thousands. An intruder is
  the same shape. It is ONE gated job, and it is gated exactly like the scanner: the four gates,
  no new ones.
* The payload set and positions are part of the approved surface, the way crawl depth and
  duration are — a fuzzer that decides its own bounds is a command that has stopped describing
  what runs.
* Reuse build #18's shaping transforms rather than growing a second encoder.
* Stop must be ungated, like every other stop in this codebase.

## 6. The HackPit MCP server — eyes, not hands

`hexstrike-ai` already gives an agent hands. What no agent can see is **this** engagement: its
scope, its capture, its findings, its KB. That is the gap this closes.

**Expose reads and PROPOSE. Never execute.**

* Reads: proxy history (filtered, item 3), scan status, alerts, session health, fronting verdicts,
  engagement scope and state, findings, KB search, arsenal, the CVE/exploit index (including the
  curated overlay), attack-path planning.
* One write-shaped tool: **`propose_command`**, which puts a command in an approval queue. A human
  approves it in the cockpit. It does not run anything.
* *** THE LINE, AND IT IS NOT NEGOTIABLE. *** The action routes take `approved=true` and
  `dangerous_ack=true` **in the request body**. If an MCP tool can set those fields, the agent
  approves itself and every gate in this codebase becomes theatre. This is exactly why
  `_gate_request` passes `GATE_KEY_PLACEHOLDER` — *the gate is never given the real thing.*
  **No MCP tool may set an approval field.** Lock it with a test that enumerates every exposed
  tool and asserts none of them can.
* Transport: stdio is simplest and needs no port. If HTTP is used it is localhost-bound, and
  note what build #19's own week taught — Burp's MCP rejects browser-looking User-Agents and
  non-allowlisted `Origin` headers as DNS-rebinding. If HackPit's MCP is HTTP, it needs the same
  protection, and route auth is still not built.
