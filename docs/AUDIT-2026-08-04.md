# HackPit — full-project end-to-end audit

**Run overnight 2026-08-04 against commit `e0749b4`, unattended, under the brief at
`docs/superpowers/prompts/2026-08-04-full-project-audit.md`.**

The question this answers is not "do the tests pass". It is *can HackPit run a real bug bounty
or a real engagement end to end today, and if not, what is missing, what is limited, and what is
blocked by a gate rather than by reality.*

---

## 0. Rules of engagement — compliance statement, stated first

**§1.1 was not breached.** Against the Majid Al Futtaim Lifestyle (Bugcrowd) assets:

* **No active scanning of any kind** touched a third-party host. No `ffuf`, no `sqlmap`, no
  `nuclei`, no `zaproxy`, no brute-forcing, no fuzzing.
* Exactly **one** packet-generating command was executed against a program asset all night: a
  single `dig +short www.crateandbarrel.me A`, which resolves through a resolver and is
  answered by DNS infrastructure, not by the target. It returned `crateandbarrel.edgekey.net`
  (Akamai), confirming the CDN note in the brief.
* **Nothing was submitted anywhere.**
* The planned passive HTTP fingerprint sweep (one `HEAD` per host, 3s apart, aborting on any
  403/429/captcha) was **refused by the real-time classifier** and was therefore **NOT RUN**.
  It is left as a self-verifying script for a human to run — see §6.

All intrusive testing was confined to the isolated lab (`hackpit-lab-target`, Juice Shop) and to
Zaid's own domain controller (`192.168.13.140`).

## 2. The safety spine — every gate proven to fire AND proven able to fail

The 2026-07-27 audit found seven guards that existed and never fired, and the brief said to
assume there is an eighth. **There is not one among the core spine.** A harness drove the real
`executor.validate_request` with a refusal *and* a positive control for every gate, in both lab
and engagement mode: **24 checks, 0 failures**, plus **3 more** on the isolation guard.

| Gate | Fires on | Positive control |
|---|---|---|
| `target` (lab) | internet host · LAN host · a command naming no host · a payload hidden in a `-c` string | the lab target clears it |
| `approval` | `approved=false` | `approved=true` clears it |
| `danger` | `nc -e` · `sqlmap --os-shell` · `msfconsole` · `python3 -c` | the same command **with** `dangerous_ack` clears it; a benign `nmap` is never flagged |
| `engagement` | an unknown id — and it is **not** silently downgraded to lab | — |
| `target` (engagement) | a host outside the program scope | an in-scope host **and** an in-scope `*.wildcard` host both clear it |
| `approval` (engagement) | `approved=false` on a **real** target | — |
| `danger` (engagement) | a dangerous real-target command still needs the red-confirm | — |
| `windows` | an unknown profile id | — |
| `sandbox` (isolation) | a container with a **real** egress path · a container that does not exist | the real isolated lab sandbox is accepted |

The isolation refusal is worth quoting because it was proven with a genuinely non-isolated
container rather than a mock — pointing the lab guard at `hackpit-engage-sandbox` (deliberately
fully open, Wall A down) produced:

> `sandbox is attached to non-internal network(s) ['hackpit-cockpit_hackpit-engage'] — that is
> an egress path; refusing to execute`

**A trap worth recording.** The first version of that harness probed the danger gate with
`bash -c '…10.0.0.1…'` and got `gate=target` — the target gate fires **first**, so the probe
never reached danger, and the "with ack" control passed *vacuously*. This is exactly the failure
mode the house style's "not refused at THIS gate" phrasing exists to prevent, and it caught
itself. **In lab mode the danger gate is only reachable by a command that names the lab target
as a clean argv token**; anything else is refused at `target` first. That is the safe direction,
but it means a naive danger-gate test can pass for the wrong reason.

## 3. The five questions

### 3.1 Can it run a full bug bounty today?

**Partly — and the part that works is the part that is hardest to build.** The scope model,
the gates, the grounding and the report shape are real. What is missing is everything that makes
a sweep *sustainable*: pacing, batching, dedupe, and mobile.

**Can you even express this program's scope? — YES, and better than expected.** All 11 web/API
targets parse and resolve. URLs with schemes, paths and trailing slashes reduce correctly to bare
hosts (`https://www.cb2.ae/en` → `www.cb2.ae`). Wildcards match the apex *and* subdomains,
exclusions win, and — tested explicitly — both classic wildcard bypasses are refused:

```
thatconceptstore.com            in_scope=True     (apex, correct)
api-prod.thatconceptstore.com   in_scope=True
internal.thatconceptstore.com   in_scope=False    (exclusion wins)
notthatconceptstore.com         in_scope=False    (suffix-confusion refused)
thatconceptstore.com.evil.net   in_scope=False    (suffix-append refused)
```

The engagement was created live (`eng-69ec01d0fe74`) with all 11 targets, 9 resolved IPs, and an
authorization string. Out-of-scope hosts are then genuinely refused at exec: a
`curl https://www.google.com` under that engagement is refused at `target`.

**The mobile targets — NO, and the failure is worse than "unsupported".** `parse_scope` refuses
them, which is correct-ish, but *how* it refuses matters:

```
parse_scope("THAT Concept Store iOS")
  → ValueError: could not resolve any in-scope host (DNS failed for: that, concept, store, ios)
```

The spec splits on whitespace, so an app name becomes **four bogus hostnames**. Had any one of
those four resolved (`store` under a search domain, say), the scope would have been *accepted*
with a garbage host silently in it. That is a fail-open shape hiding inside a fail-closed
result. **2 of this program's 4 scope categories cannot be represented at all.**

**Is the mobile gap worth closing? — Not as execution. Yes as scope.** HackPit has *no* mobile
execution surface, and — measured — not even a mobile *entry* in the tool catalogue (no `adb`,
`frida`, `objection`, `apktool`, `jadx`, `mobsf`). Building a mobile execution surface is a
different product: it needs a device or emulator, not a Linux container. But being unable to
*record that a mobile target is in scope* is a scope-model bug, not a product-boundary decision,
and it is cheap to fix (an `app:` pattern kind that is stored, reported, and never resolved).

**Known issues / duplicate suppression — NO. Nothing models it.** The dedupe that exists
(`state/store.py` upserts, finding fingerprints) is *internal*: re-running a scan corrects what
is known instead of duplicating it. That is good and it is not the same thing. There is no
notion of a program's disclosed known-issue list, and no way to mark a finding "already
reported". On a program running since 2019 that is the single largest source of wasted effort.

**Is the report Bugcrowd/H1-shaped? — YES, and this hypothesis in the brief was wrong.** There
is a dedicated `bugbounty` template ("You are writing a bug-bounty vulnerability report for a
HackerOne / Bugcrowd submission"), it is one of four selectable templates, and it **is wired into
the UI** (`ReportScreen.tsx`: *"Bug bounty (H1/Bugcrowd + CVSS)"*). There is a real CVSS 3.1 base
calculator, and it is correct — verified against six known vectors including the round-up edge
cases:

```
AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H → 9.8 Critical    AV:N/AC:L/PR:N/UI:R/S:C/C:L/I:L/A:N → 6.1 Medium
AV:N/AC:L/PR:L/UI:N/S:U/C:H/I:N/A:N → 6.5 Medium      AV:N/AC:H/PR:N/UI:N/S:U/C:N/I:N/A:L → 3.7 Low
a vector with no CVSS: prefix       → 9.8 (accepted)  garbage                             → None
```

What is genuinely missing on the reporting side is narrower than the hypothesis suggested:
**no VRT** (Bugcrowd's taxonomy), **no P1–P4 mapping**, and **CVSS 3.1 only, not 4.0**.

**Where does it stop being usable?** At volume. Everything above is per-finding and works. A
real sweep of hundreds of endpoints hits three walls at once — no throttle, no batching, no
dedupe — covered in 3.4.

### 3.2 What is limited *by the lab* rather than by design?

Zaid's instruction was that anything limited only by the lab can skip the lab case and ship for
engagements. Auditing for that, the honest answer is **almost nothing qualifies**, which is a
good result:

* **Lab target-lock requires the argv to name the lab.** This is the one true lab-only
  constraint, and it is *why* the danger gate is hard to reach in lab mode. It does not apply in
  engagement mode, where the program scope is the lock. Nothing to change.
* **Active scanning is bounded by what the proxy captured** (`url_not_found`). That is a ZAP
  property, not a lab property — it holds identically in engagement mode. It is a bound, not a
  limitation to lift.
* **Browser interception is blocked** — and this is *not* a lab limitation either. It is blocked
  by a measured product fact (§3.3).

The one item that genuinely reads as lab-shaped — **the isolation floor** — is already
engagement-exempt by design (Wall A down, proven 4/4 tonight). So there is no backlog here.

### 3.3 Is any gate restricting something legitimate?

**No gate is over-tight. The problem is the opposite — one gate is missing.**

Every refusal observed all night was correct, and the danger gate never blocks outright: it
requires a second confirm and then proceeds. Measured against real bug-bounty work:

> `ffuf -u https://www.crateandbarrel.me/FUZZ -w common.txt` → **passes on `approved=true` alone**
> `sqlmap -u https://api-prod.thatconceptstore.com/x?id=1 --batch` → **passes**
> `nuclei -u https://lego.me -t cves/` → **passes**

These are precisely the commands §1.1 forbids and that most programs' automation clauses forbid,
and they carry **no red-confirm** against a third-party production host. This is not a bug in the
danger heuristic — that heuristic models *arbitrary code execution and danger to the operator*,
and it is right that `sqlmap --batch` is not that (it correctly flags `sqlmap --os-shell`).

**The gap is that nothing models aggression toward the target.** The narrowest fix is a fifth
gate that fires only in engagement mode, on high-volume/automated tooling, and asks for the same
red-confirm the danger gate already uses — reusing the existing mechanism rather than inventing
one. It should say what it is protecting: *"this sends automated high-volume traffic to a
third-party production host; most programs' automation clauses forbid it."*

### 3.4 What is missing for real-world engagements? (features, not polish)

Ordered by how much each one costs you on a real program:

1. **No rate limiting or pacing, anywhere.** Measured: no throttle, no delay, no
   requests-per-second control, no concurrency cap in `cockpit/`, `state/`, `reasoning/` or
   `arsenal/`. Nothing even suggests `--rate-limit` in tool invocations. Combined with 3.3 this
   is the single biggest real-world gap: HackPit will happily drive an unthrottled scanner at a
   production retail site.
2. **No known-issue / duplicate suppression** (3.1).
3. **No authenticated scanning.** HackPit configures no ZAP contexts — the code says so directly
   — so anything behind a login is unreachable by the active scanner. On an e-commerce program
   where the interesting logic is post-login, this excludes most of the attack surface.
4. **No mobile scope representation** (3.1); mobile execution is a defensible product boundary,
   mobile *scope* is not.
5. **No VRT / P1–P4**, CVSS 3.1 only.
6. **Engagements never expire.** There are **21 engagements simultaneously active** right now,
   almost all stale test runs from previous sessions, several scoped to internal CIDRs and to the
   DC. Nothing is unsafe — every one still requires per-command approval — but an engagement
   record is an *authorization* record, and authorization that outlives the engagement is the
   wrong default. There is no exit-on-idle, no expiry, and the UI shows one arbitrary active
   engagement in the status rail.
7. **Approve-every-command has no batching, by design — and the design is right.** There is no
   batch, no approve-all, no autonomy, enforced and commented in three places in `executor.py`.
   For a bug-bounty sweep of hundreds of endpoints this *is* the friction it sounds like, but the
   answer is not to weaken it. The tools that generate volume (`ffuf`, `nuclei`, ZAP's active
   scanner) are already **single approvals that produce thousands of requests** — one approval
   bought 374 attack requests in tonight's scan proof. The per-command gate is therefore not the
   bottleneck people assume; the missing piece is pacing *inside* an approved run (item 1), not
   batching *across* approvals.

### 3.5 Is the build done?

**No — but it is much closer than the hypothesis list implies, and two of those hypotheses were
simply wrong.**

Done and genuinely strong: the safety spine (27/27 tonight), the scope model, the isolation
story, the Windows/AD path, the KB grounding, the proof discipline, the report templates and
CVSS.

The list that would make it done, smallest first:

1. Fix the mobile-scope parse (an `app:` pattern kind) — hours.
2. Add the third-party-aggression red-confirm (§3.3) — hours, reuses the danger mechanism.
3. Add pacing to engagement-mode runs — days.
4. Known-issue suppression — days.
5. Authenticated scanning (ZAP contexts) — days.
6. Engagement expiry — hours.
7. **Route auth** — the blocker for anything that is not localhost (§4).

## 5. Defects found, and what was done

### Fixed and shipped in this commit

**B1 — two tool files were unaddressable and silently dropped from the Scripts Arsenal.**
`pipeline/ingest_corpora.py` built a tool-file id from `path.stem`, which drops the extension, so
files differing only by suffix collided:

```
toolfile-network-utilities-nc        -> Network Utilities/nc      (linux)
toolfile-network-utilities-nc        -> Network Utilities/nc.exe  (windows)
toolfile-active-directory-sharphound -> SharpHound.exe  and  SharpHound.ps1
```

The extension is not decoration here — it is what decides `platform`, so the Linux `nc` and the
Windows `nc.exe` are genuinely different artefacts. Two consequences: `/entry/{id}` could only
ever resolve one of each pair, and because the Scripts Arsenal keys its React list on that id,
**React dropped one of each pair from the rendered list** (two duplicate-key errors in the
console, confirmed in the browser). Fixed at source (`path.name`), the derived artefacts were
regenerated, and it is now locked by two tests — one on the derivation with a control proving the
*old* derivation collided, one on the built artefact.

**B2 — the Scripts Arsenal claimed more scripts than it contained.** The section header printed
`group.count` (every distinct script) while the list held `group.shown` (what survived
`MAX_PER_TYPE`), and the page subtitle quoted the full total. Measured: **1235 claimed, 1158
served**; `Enumeration` claimed 335 and rendered 263. The cap is deliberate and the pipeline
honestly records both numbers — the UI just never used `shown`, which was already carried all the
way through the backend model and the API type. Now the header shows what is actually listed and
a note states plainly how many were dropped, by which cap, and that the filter cannot reach them.

**B3 — the scripts index was stale by 126 KB entries** (built against 2617, KB has 2743).
Rebuilt. Nothing detects this drift; see the punch list.

**B4 — checkboxes rendered as wide grey slabs on every screen except `:proxy`.**
`.hp-tn-form input { flex: 1 1 200px }` over-matches: a checkbox is not a text field. `:proxy`
worked around this per-screen with `.hp-tn-check` after build #14 part 3 found it; `:exposure`
(four checkboxes), `:repeater`, `:oob`, `:cockpit` and the AD screens still had it. **Fixed in the
CSS rule itself rather than in each component** — the defect is in the over-matching predicate,
so the fix belongs where every screen gets it. Verified in the browser before and after.

**C1 — real captured domain credentials were configured to be sent to a remote LLM.**
`state/render.py` sets `INCLUDE_CREDENTIAL_SECRETS = True`. That is Zaid's explicit, documented
decision and the code is admirably blunt about the consequence: *"every captured credential is
sent to whatever LLM endpoint is configured, including a remote one."* The decision is safe under
its unstated precondition — a local endpoint. **That precondition was not holding.** The live
provider was `claude-agent-sdk` (remote, model `opus`), while six real credentials from the build
#9 live fire sit in `state_credentials`. The next planner call on that session would have shipped
them off-box. Per the brief's standing rule ("Ollama, never the Agent SDK") the provider is now
**`ollama` / `qwen3:8b`**, verified working end to end (a grounded attack path composed in 147s,
`context_leaks=0`, steps citing real KB entry ids).

This is the finding I would most want Zaid to read. Neither half is a bug; the combination was.

### Found, not fixed (in the punch list)

**D1 — the mobile-scope whitespace split** (§3.1) — fail-open shape, needs a design decision.
**D2 — no third-party-aggression gate** (§3.3).
**D3 — no pacing** (§3.4).
**D4 — engagements never expire**; 21 active.
**D5 — the safety suite rewrites the live, gitignored KB on every run.** `test_reingest_is_byte_identical`
re-runs the real ingester against `data/kb/entries.jsonl`. It asserts byte-identity and it held
tonight (`recovered_from_git: 23`, 2743 → 2743, byte-identical), but a green test run mutating
production data with no restore path is a standing hazard — it is exactly how last night's build
lost an entry.
**D6 — no drift detection between the KB and its derived artefacts** (B3 went unnoticed).
**D7 — WinRM surfaces CLIXML progress records as stderr.** Every successful AD command returns
`rc=0` alongside a wall of `#< CLIXML <Objs Version=…>`. Known trap, cosmetic, but it makes a
clean run look like a failing one.
**D8 — planner commands are raw KB excerpts, not runnable.** Measured twice. With the correct
request shape (`goal` + `target_type=web` + `scope_text="www.crateandbarrel.me,
api-prod.thatconceptstore.com"`), the response came back `scoped=False` and of **32 commands,
0 named the real scope** while 4 carried a foreign example (`https://<tenant>/…`,
`login.microsoftonline.com`). An earlier run returned `sublist3r -d tesla.com -t 100 / above the
-t is for threads…` — the source writeup's own example host *and* its prose, verbatim, inside the
`cmd` field. Each step carries a `target_adaptation` that *describes* the substitution in words,
but nothing performs it. The operator must retype essentially every command.

Related and smaller: `/attack-path` accepts only `goal`, `target_type`, `scope_text`. A `target`
field passed by a caller is **silently dropped** rather than rejected, which is how the first
measurement above initially looked worse than it was.
**D9 — `:evasion` and `:ad-graph` use a different visual language** from the other 16 surfaces
(no kicker/`:title` header block, different card and button styling). Cosmetic, but they read as
belonging to a different product.

## 8. What is genuinely strong

Said plainly, because an audit that only lists defects misrepresents the thing it audited.

* **The gate design holds up under adversarial probing.** 27 checks, both directions, two modes,
  zero failures — and the one confusing result was my harness's fault, caught by the project's own
  "not refused at THIS gate" convention.
* **The scope model is better than the brief assumed** and refuses the wildcard bypasses that
  real scope checkers get wrong.
* **Observed-not-assumed is real.** `:arsenal` says *"105 of 110 catalogued Linux tools are
  installed"* and names the five that are not. `:terminal` reports `0/3 live`. Status comes from
  probing, not from hope. B2 was notable precisely because it was the rare place that broke this
  rule.
* **The code is honest about its own risks in the exact places it matters** — `render.py` states
  the credential consequence in full; `proxy.py` explains why `inScopeOnly=false` and warns
  against "tightening" it. C1 was found *because* the code said what it did.
* **Windows/AD is live, not theoretical.** Real WinRM to a real DC, real domain enumeration
  through the gated executor, DCSync-shaped commands correctly red-confirmed.
