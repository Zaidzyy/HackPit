## The measurement everything here rests on

Build #17 established, against a live Akamai-fronted target, that **there are two different walls
and they need different answers**:

| wall | what it judges | what happened | what fixes it |
|---|---|---|---|
| **Bot Manager** | the CLIENT | headless Chromium → 504 tarpit; bare `curl`/`ffuf`/`nuclei` never reach request one | a real browser (done, build #17), or a browser-fidelity HTTP client (item 5) |
| **WAF rules** | the REQUEST CONTENT | scanner payloads → **36 of 39 got `403 AkamaiGHost`** | a program bypass header (item 1), the origin (item 2), a narrower policy (item 3), payload shaping (item 4) |

**Do not conflate them again.** Fingerprint spoofing does nothing about the 403 — those requests
already cleared Bot Manager and died at the rule engine. This was got wrong once already.

Also measured: the discriminator for headless is the **absence of `Sec-CH-UA` Client Hints**, not
the `HeadlessChrome` token. Spoofing the User-Agent failed identically to not spoofing it.

## *** THE BUILD IS UNRESTRICTIVE. THIS IS A REQUIREMENT, NOT A PREFERENCE. ***

HackPit's design is that **the operator is the bound and every control informs rather than
forbids**. The danger gate demands a second confirm and then proceeds. The scope lock is
documented in its own docstring as a handrail, not a wall. Build #17 *declined* to make the
authorization field enforceable, and then had to strip three prohibitions its own proof script
had invented — including one that would have refused ten of the eleven in-scope hosts.

So, while building this:

* **Do NOT add a gate, a flag, a confirm, a blocklist or an allow-list narrowing.** Not in the
  product, and not in a test or proof script either. A harness must never invent a prohibition
  the product does not have.
* **Do NOT weaken the existing safety spine either.** Never widen a safety allow-list so new code
  fits — fix the predicate. Keep secrets out of run records, LLM prompts and reports.
* Where something could refuse or could warn, **warn and continue**, and say why once.
* When a decision comes up overnight, **take it, build it, and record it in the assessment.**
  Do not stop and wait. The only thing worth stopping for is a discovery that makes the plan
  itself wrong, and even then: record it, do the rest, and say so at the end.

## How to work (the environment, learned the hard way)

* **Live fire against a real target is refused by the real-time classifier from inside the agent
  session.** Every real-target verification must land as **one self-verifying script** under
  `docs/proof/`, printing a `VERDICT=` line and exiting non-zero on failure, for Zaid to run in a
  plain shell. `docs/proof/build17_run.sh` is the model.
* **Gate every verification on a CAPTURED exit code**: `cmd > log 2>&1; echo "EXIT=$?"`.
  `cmd | tail && git commit` does NOT gate. **And `RC=$?` after a pipe is TEE'S status**, which is
  0 whenever tee could write the file — build #17 shipped that bug into two wrappers before
  catching it. Stash the real status through the pipe.
* **An image rebuild is ~45 minutes and recreating a container destroys the ZAP daemon and its
  capture.** Bundle EVERY image change into ONE rebuild, at the END. `docker compose` takes the
  SERVICE name (`engage-sandbox`), everything else takes the CONTAINER (`hackpit-engage-sandbox`).
* `git push` works via the **PowerShell** tool when Bash is refused. So does `python -m py_compile`.
* The console is **cp1252**: printing `→` or `§` from a verification script raises
  `UnicodeEncodeError`. Print ASCII, or `.encode("ascii","replace")`.
* `test_redirector.py` flakes on Windows UDP excluded-port ranges. One red run of that file is not
  evidence until repeated.

## 1. Per-engagement bypass header — the highest value per line in this plan

Programs of MAF's size issue researchers a header that skips the WAF. Zaid does not have one yet.
Build the mechanism now so it is ready the day he does.

* A header **name + value** stored on the engagement (`EngagementRecord` / `engagement.py`), set
  when entering or amended after. More than one header must be possible — programs issue pairs.
* Injected on **every request that leaves through the proxy, including the active scanner's**.
  The clean single point is ZAP's **Replacer** add-on (`replacer/action/addReplacerRule` with
  `matchType=REQ_HEADER`), not our own per-call plumbing — one rule covers browsing, spider and
  scan alike. Read the rules back (`replacer/view/rules`); **an OK is not a result**, and this
  codebase has been bitten by exactly that on `setOptionBrowserId`.
* **THE VALUE IS A CREDENTIAL.** It must not reach a run record, the LLM prompt, or a rendered
  report. Reuse build #15's pattern: the gate is never given the real value, and `secretargs`
  masks it anyway. Key the mask on the SETTING, not the flag — that lesson is written up in the
  assessment's "the key is closed twice" section.
* **ZAP PERSISTS ITS CONFIGURATION.** A replacer rule set for one engagement and never removed
  will silently apply to the next one. Remove the rule on engagement exit and on proxy stop, and
  make `observed_*` report the rules ZAP actually holds. *"A daemon that persists its
  configuration makes every measurement conditional on what a previous run wrote."*
* **Verify with a dummy header**, end to end: set it, drive one request through the proxy, read it
  back out of ZAP's history and assert the header is on the OUTGOING request. That is provable
  without a real bypass header and without touching a real target.

## 2. Is it CDN-fronted, and what is behind it?

Passive/OSINT only. **No scanning, no brute force** — this answers a question, it does not attack.

* For each in-scope host: resolve the CNAME chain, read the `Server` header, map the IP to an ASN,
  and say plainly **fronted / not fronted / unknown**.
* Surface candidate origins from passive sources: certificate transparency, historical DNS, SPF
  and MX records. These are lookups, not probes.
* **Answer the concrete question this build exists for:** are `api-prod.thatconceptstore.com` and
  `lapi.yellowblocks.me` Akamai-fronted, or are they reachable directly? Two of eleven hosts might
  need none of the rest of this plan.
* A discovered origin IP is **out of scope until the scope says otherwise.** Report it; do not
  auto-add it. `add_pivot_subnet` is the one deliberate, audited widening path and a human uses it.

## 3. Scan policy — fewer, better requests

Most of the 403s came from checks that could never have applied. Firing Shellshock at a Next.js
storefront costs a request, earns a WAF hit, and cannot find anything.

* Named scan policies on `ScanStartRequest` (e.g. `targeted-web` vs ZAP's default), configured
  through `ascan/action/setPolicyAttackStrength` / `setPolicyAlertThreshold` and the plugin-enable
  actions. **Read the policy back.**
* Same persistence trap as item 1: a policy set on the daemon outlives the scan. Reset it, and
  report what ZAP holds rather than what we sent.
* **State the measured claim**: requests sent, 403 share, and alerts raised, default policy vs
  targeted, against a lab target. If the narrower policy does not measurably help, say so — a
  negative result recorded is worth more than a feature that quietly does nothing.

## 4. Payload shaping — Zaid's call, taken explicitly

Encoding, case variation, comment insertion, chunking, parameter pollution. Legitimate on a
safe-harbour program; Zaid has taken the decision and it is not to be re-argued.

* **Be honest about feasibility first.** ZAP's API does not cleanly expose arbitrary payload
  mutation for the active scanner. Investigate the real options — the Custom Payloads add-on,
  input-vector configuration, scan-policy variants — and **if the scanner cannot do it, say so and
  build it where it CAN work: the repeater path**, which is operator-driven and already exists.
  A documented "the scanner cannot, the repeater can" is a good outcome; a fake knob is not.
* It is an explicit per-scan/per-request option. That is ordinary engineering, **not a gate** —
  no confirm, no ack, no refusal if unset.
* Measure it: same request, shaped vs unshaped, and report whether the 403 becomes a 200. Against
  the LAB target with a rule that mimics a signature match — do not burn real-target requests
  discovering that an encoder works.

## 5. Fingerprint spoofing — for the BARE TOOLS, not the scanner

This is the answer to Bot Manager, and its value is that `ffuf`, `nuclei`, `httpx` and `curl`
currently **never reach request one** against nine of eleven hosts (h2 stream reset, h1.1 timeout).

* Install a browser-fidelity HTTP client into the sandbox image — `curl-impersonate` is the
  obvious candidate (real Chrome/Firefox JA3/JA4 TLS handshake, HTTP/2 SETTINGS and frame order,
  and the full header set including Client Hints).
* **Bundle this into the SAME image rebuild as anything else** that touches the image. One rebuild.
* Make it reachable as a normal HackPit capability, gated exactly like every other tool — the
  existing four gates, no new ones.
* **Prove the version string is not the result.** Build #15's lesson, one level deeper: proving the
  binary runs proves nothing. The proof must be that a request a bare `curl` cannot complete
  succeeds through the impersonating client. That needs a real WAF-fronted host, so it goes in the
  live-fire script for Zaid.
* Record what it costs honestly: this is a tool that makes HackPit's traffic indistinguishable from
  a browser's. It is being built deliberately, for an authorized safe-harbour program.

## 6. Authenticated scanning, Tier 2 — the session you established by hand

**The hard part already exists.** Your manual Firefox login through the published proxy puts a
live session inside ZAP. What is missing is telling ZAP's scanner what it means.

* Create a **Context** for the target (`context/action/newContext`, `includeInContext`).
* **Cookie-based session management** (`sessionManagement/action/setSessionManagementMethod`).
* **Logged-in and logged-out indicators** — regexes that match a logout link vs a login form
  (`authentication/action/setLoggedInIndicator` / `setLoggedOutIndicator`).
* Scan **within the context**, so the scanner knows when it is authenticated.
* This makes build #16's session-expiry detection meaningful for the first time — build #17 found
  it was reading `history(count=200)` from the OLDEST end and therefore could never fire. It reads
  the newest window now.
* Verify end to end **against the lab target**: log in, scan, confirm the scanner reaches
  post-login URLs and that killing the session flips the health verdict to `suspect`.

## 7. Authenticated scanning, Tier 3 — with the trap named

Full automation: form/script-based auth, stored credentials, automatic re-login.

* Credentials come from **`state/credvault.py`**, never from an argv, never from a run record.
* Form-based authentication method + a user, and re-authentication when the logged-out indicator
  matches mid-scan.
* **THE TRAP, STATED SO IT IS ENTERED WITH EYES OPEN:** build #15 avoided this deliberately, on
  the grounds that per-target auth scripting is a problem the codebase would then own forever.
  Zaid has chosen to take it on. Keep it as close to declarative as possible — a form selector, a
  username field, a password field, indicators — and resist growing a scripting language.
* **Zaid has no account on any in-scope host.** So Tier 3 is verified against the LAB target ONLY,
  and the assessment must say **UNVERIFIED against a real target** in those words. Do not imply
  otherwise. Tier 2 is unaffected — it needs no credentials at all.

## 8. The silent-empty sweep — build #17's durable lesson

Three defects in build #17 were the same shape: **an error path that returns empty and reads as
"nothing is there."** The key was lost → `[]`. The bytes would not decode → `[]`. The window was
wrong → `[]`. Each looked like a confident, successful zero.

* Scan `backend/cockpit/`, `backend/state/`, `backend/arsenal/` and `backend/reasoning/` for the
  pattern: an exception handler or a falsy guard that returns `[]`, `""`, `{}` or `0` where the
  caller cannot distinguish "empty" from "failed".
* **AST, not substring** — docstrings fool a grep, and this repo has been caught by that. Note
  also that `sorted(a_dict)` yields keys, so a shape change there fails SILENTLY.
* Report every hit; fix the ones where a caller genuinely cannot tell. Not every empty return is a
  defect — say which are fine and why.
* This is a *finding* item as much as a fixing one. A list of them in the assessment is the
  deliverable even if only two get fixed.

## 9. KB ingest — the new source

`sources/random Custom Toolsmini scripts for.txt` (HTB helper scripts).

* **Expect LOW yield and do not force it.** The useful content is the file-transfer / ingress
  tool-transfer one-liner catalogue (PowerShell, cmd, Linux, `/dev/tcp`, netcat variants) — that
  maps to **T1105**. The random-box picker and the nmap wrapper are noise.
* Prior batches recorded the discipline: 24 repos → 2 entries, 7 gitbook spaces → **zero**. The
  token diff NOMINATES candidates and never confirms a gap. One good authored entry beats six
  padded ones.
* **`data/kb/entries.jsonl` is gitignored and sits at 2743.** If this item adds entries, record
  the NEW count in the assessment and verify it after the run — **Defender has quarantined that
  file before**, so check it still exists and the count is what you expect.
* Re-run `test_corpora` after; it is known to flake immediately after an ingest — re-run before
  believing a failure.
