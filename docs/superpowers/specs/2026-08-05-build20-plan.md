## 1. VERIFY ZAP'S GRAPHQL API FIRST — go/no-go for items 4 and 5

Nothing in items 4 or 5 may be built before this answers. This exact discipline has now paid off
twice: build #14 was written against `zap-baseline.py`, which does not exist in Kali; build #19
found **four of its five** assumed break-API facts were wrong, plus a `drop`-with-nothing-held
that permanently wedges the break manager.

The add-on is `graphql-alpha-0.33.0` — **alpha**. Assume nothing from its documentation.

* Bring a daemon up (`docker/proof/browser_intercept_proof.sh` drives its own, or start one from
  `:proxy`; 8090's publish state may need re-applying).
* Enumerate what `graphql/` actually exposes in THIS build — views and actions, by name, with
  their real parameters. Do not trust an online reference for a version you are not running.
* The shapes this build needs, each confirmed or denied by name:
  1. import a schema **by introspection URL**, and by **file/text**
  2. read back what was imported — an OK is not a result
  3. control query-generation depth / mutation handling (the approved bounds)
  4. whether generated operations land in the **Sites tree** such that `ascan` can attack them
  5. whether the active scanner can target a **single GraphQL argument** rather than the whole
     JSON body — this is the one report #61 needs
* Also enumerate ZAP's **input vectors** for the active scanner (JSON body specifically), because
  that is the fallback if the GraphQL add-on cannot aim at an argument.
* **Write the result down as a proof script** under `docs/proof/`, the way build #19 did
  (`build19_break_api.py`, 27/0). If a shape is absent, **say so and cut that sub-item** — a
  recorded "ZAP cannot do this" is a legitimate outcome and worth more than a half-feature.

## 2. Detect GraphQL in captured traffic

* Recognise it by **body shape, not path**: a JSON body carrying `query` (with optional
  `operationName` / `variables`), and `GET ?query=`. Path heuristics (`/graphql`, `/api/graphql`,
  `/v1/graphql`, `/gql`) are a hint that may be reported, never the test.
* Surface it as a filter in the history filtering build #19 just added, and flag it on endpoints.
* **Report the count honestly** alongside build #18's `dropped` / `read_ok`. A detector that
  silently searched one window would be this repo's recurring silent-empty in a new place.
* Read-only, ungated, like the history it reads.

## 3. Repeater GraphQL mode — the measured pain, and this part is OURS not ZAP's

* Separate **Query** and **Variables** editing, serialised into a correct JSON body, so nobody
  hand-writes quadruple-escaped JSON-in-JSON again.
* **Round-trip**: parse a captured GraphQL request INTO query + variables, let the operator edit,
  re-serialise. A request that will not parse must fall back to the raw body and say so — never
  silently discard what the operator captured.
* *** THE OPERATOR'S RAW BODY WINS. *** If they edit the raw body directly, the structured
  editor must not overwrite it. This is the same rule build #19 applied to the cookie jar — the
  operator's typed cookie wins — and for the same reason: state that silently rewrites a request
  is a trap.
* The repeater stays **HUMAN-ONLY**. That is locked by `test_repeater.py`; do not touch it.

## 4. Introspection + schema import

* Fetch the schema by introspection; list types, queries, mutations and their arguments.
* *** INTROSPECTION DISABLED IS NOT AN EMPTY SCHEMA. *** Production commonly turns it off, and
  the two must be different answers — `disabled` / `error` / `empty` are three facts and the
  operator needs to know which. Returning `[]` for all three is precisely the silent-empty class
  build #18 spent an item on.
* Depth and generation bounds are part of the **approved surface**, for the same reason crawl
  depth and duration are: a generator that decides its own bounds has stopped describing what runs.
* **ZAP PERSISTS ITS CONFIGURATION**, add-on options included. Set from a known baseline, read
  back, and do not let one engagement's settings silently condition the next. This has bitten
  this project twice (`api.disablekey`, the scan policy).
* Out of scope, and say so rather than half-doing it: **field-suggestion / clairvoyance
  enumeration** when introspection is off. Record it as a known gap.

## 5. Scanner injection into GraphQL arguments

Only in whatever form item 1 proved. This is what report #61 actually needs.

* Prefer ZAP's own path — generated operations in the Sites tree, then `ascan` against them.
* If the add-on cannot aim at a single argument, fall back to ZAP's **JSON input vector** and say
  clearly, in the assessment, which one is in use and what it can and cannot reach.
* It is a scan: it runs behind **the existing four gates**, exactly like the active scanner. **No
  new gate.** Stop stays ungated.
* Reuse build #18's shaping transforms rather than growing a second encoder.
* Measure it: requests sent, arguments reached, alerts raised — against a lab target, not a real
  one.

## 6. Arsenal — the standard GraphQL tools

The arsenal has none. Add the ones that are real and packaged: `graphw00f` (engine
fingerprinting), `graphql-cop` (audit), `inql` (introspection/schema), and `clairvoyance` if it
installs cleanly.

* Follow the existing catalog conventions exactly. **Never name a placeholder `<lhost>`** — that
  lesson is in the arsenal notes.
* Whatever cannot be installed cleanly in the image, **leave out and say why**. Kali ships some
  tools under different binary names than their project names; the image build is what proves it,
  not the package name.
* Bundle any image change into **ONE rebuild at the END** — it is ~45 minutes and recreating the
  container destroys the running daemon and its capture.

## 7. Look at it in a real browser

The Chrome extension **is connected now**. Build #19 could not use it and fell back to
screenshotting the sandbox's own Chromium via `host.docker.internal:3000` — which still found two
defects nothing else could: a shared CSS rule that never named `textarea`, and JSX dropping a
space that was present in the source.

* **Read the `frontend-class-vocabulary` memory BEFORE touching a screen.** Bare `.hp-card` is
  `opacity:0`; screens use `hp-tn-*`.
* `tsc`, `next build` and `eslint` **cannot see whether a CSS class exists**. A frontend change is
  not verified until it has been LOOKED AT.
* Drive the real Chrome over every screen this build touches, and say in the assessment what you
  looked at and what you found.
